# Implementation Gap Report

See `MANUSCRIPT_IMPLEMENTATION_AUDIT.md` for the headline finding (repository predates and does not implement the manuscript's architecture) and `MANUSCRIPT_TO_CODE_TRACEABILITY.md` for the row-by-row evidence this report summarises.

## A. Critical scientific mismatches

1. **No LPU/FLA architecture exists.** The manuscript's central contribution — separating operational decisioning from independent fairness auditing — has no repository counterpart. There is one flat script sequence with no role boundary, so none of the manuscript's aggregate-statistics or fairness-metric claims (C_k, A_k, P_k, TP_k, N_k, FP_k, Δ_DP, Δ_EO) can be evaluated, reproduced, or falsified from this repo.
2. **Credit-score computation is a hardcoded constant** (`CIBIL_score = 550` in `Apply_loan.py`), not a function of employment status, salary, or credit history as Algorithm 3 specifies. Any claim that the prototype "computes" creditworthiness is unsupported.
3. **The one existing decision rule inverts the manuscript's design intent.** `Approval_decision.py` conditions the loan/interest-rate outcome directly on decrypted protected-attribute match flags (`check_gender`, `check_casteCat`), i.e., the repository's actual business logic uses protected attributes as a decision input for benefit-scheme eligibility — the opposite of "gender must not be used by the decision-making entity."
4. **No credit-score threshold τ or Ŷ_i=I[s_i≥τ] exists**, so there is no way to verify the manuscript's claim that "threshold satisfaction is not used as a condition for including an application in the fairness-audit population" — the population/inclusion logic itself does not exist.
5. **No LendingClub pipeline, synthetic-gender generator, or fairness-metric code exists.** All of §6 (Evaluation Design) — dataset loading, 70/10/20 split, proxy-feature construction, α0/α1 sampling, logistic/random-forest decision models, DP/EO computation, reconstruction-error computation — has zero corresponding code, data file, or notebook cell.

## B. Security/privacy mismatches

1. **CRITICAL — the code that makes the eligibility decision decrypts the encrypted protected-attribute comparison result directly** (`Loan_approval.py`: `SoP_gender.decrypt()`, and identically for caste/religion/orientation/ethnicity). This is the exact behaviour Threat 1 and the "LPU must not receive plaintext gender" security goal are designed to prevent. There is no code path in the repository where a decision-making role only ever sees a ciphertext of gender/caste/etc.
2. **CRITICAL — no `sk_HE`/FLA custody boundary exists.** `Enter_details.py::context()` builds one secret-key-bearing TenSEAL context, reused by the same process/script that also computes and reveals the match outcome. There is no second, secret-lacking context ever constructed, so the manuscript's central invariant ("`sk_HE` remains exclusively with FLA") cannot be satisfied by construction — there is no FLA.
3. **CRITICAL — no digital-signature scheme exists for Bank/CA/IP credentials.** `Key_generation.py` produces only RSA encryption key pairs; the sole `.sign()` call in the repository (`Decrypt_verification.py`) references an undefined variable (`private_key`) and would raise `NameError` at runtime, and signs an unrelated loan-summary text file, not a Bank/CA/IP credential. A borrower or forger has nothing to defeat, because there is no signature to forge in the first place — Threats 2 and 3 (substituted credentials, substituted gender ciphertext) have no corresponding mitigation in code.
4. **The repository's "NIZKP" function (`Account open.py::NIZKP`) is not zero-knowledge, not non-interactive, and does not implement R_acc/R_score/R_bind.** It reuses one commitment/challenge pair across four independent secrets, so its verification equation is only satisfiable when those four hashed values coincide (which will essentially never hold for real, distinct PII fields) — this looks like a latent correctness bug in the 2023 prototype independent of the manuscript's requirements, and it has zero relation to Bank-signature/account-commitment/score-commitment/application-binding statements. Because the manuscript explicitly disclaims a concrete NIZKP implementation, this is not scored against the manuscript — but see Documentation gap D.3 below for the naming-collision risk.
5. Per-record protected-attribute match results are computed and printed/decrypted for a single applicant at a time; nothing in the repository resembles "aggregate-only disclosure" — there is no aggregation step to audit for that property, so the property is trivially and completely absent rather than partially met.

## C. Experimental reproducibility gaps

1. **No benchmark harness for Figures 3–4** (phase-level computation/communication timings, batch sizes 1→100). No `time.time()`/`timeit` instrumentation, no batching loop, and the referenced image files (`Computation-cost.png`, `communication-cost.png`) are not present anywhere in the repo (`image/` and `Results/` contain unrelated 2023 screenshots of the caste/gender eligibility demo).
2. **No serialization-size measurement code** for Table 7. The manuscript resolves internally that these are analytical estimates (Consistency Finding #2 in the companion audit doc), which is at least consistent with "no measurement code found" — but a reader cannot independently confirm the arithmetic without re-deriving it from the stated CKKS parameters (which this audit did spot-check and found internally consistent: 2×8192×3×8=393,216 bytes checks out as the stated fresh-ciphertext raw size at 3 active moduli).
3. **No data availability.** No LendingClub CSV, no download script, no `requirements.txt`/environment file pinning `pandas`/`scikit-learn`/TenSEAL/`petlib`/`cryptography` versions. A fresh clone cannot install dependencies from any manifest in the repo (User Guide only says `pip install tenseal` and `pip install petlib` ad hoc).
4. **No tests.** `find . -iname "*test*"` returns nothing. There is no automated way to check any of the scientific invariants requested in Section 19 of the audit brief (matching correctness, C_k/A_k inclusion rules, DP/EO agreement, key-isolation) because the constructs those invariants refer to do not exist.
5. **The notebook does not run cleanly as committed** — cell 54's saved output includes a `TypeError` traceback, and a separately-visible traceback shows a `NameError`-shaped failure pattern (undefined `PII` in a later cell), indicating the notebook was not run start-to-finish successfully before being committed, or relies on hidden interactive state (e.g. `input()` prompts and previously-defined globals from cells run out of order in a live Colab session).

## D. Documentation mismatches

1. **README.md** claims the tool "conceals sensitive personal information, such as gender and caste category, from bank officers to ensure unbiased decision-making" and that it employs "zero-knowledge proofs to enable bank officers to verify applicant eligibility without accessing confidential data." The actual code path the officer-facing script executes (`Loan_approval.py`) decrypts the protected-attribute comparison outcome directly — the opposite of the claim.
2. **README.md** claims "Zero-Knowledge Proofs... safeguarding privacy and preventing unauthorised access" as a system benefit; the repository's only `NIZKP`-named function is a broken discrete-log Schnorr-style construction over PII fields, unrelated to protecting gender/caste, and does not achieve zero-knowledge in the sense used (see Gap B.4).
3. **Naming collision risk between repo and manuscript.** The repository's `NIZKP()` function name coincides with the manuscript's `Π_NIZK`/NIZKP terminology, but implements a completely unrelated (and broken) protocol for unrelated statements (PII knowledge, not R_acc/R_score/R_bind). A reader skimming file names risks concluding the manuscript's NIZKP relations are prototyped when they are not. This should be corrected before linking the repo from the paper, e.g. by renaming/removing the legacy function or adding an explicit README note that it predates and is unrelated to the manuscript's NIZKP formalisation.
4. **User Guide.md** still points to a different upstream repo name (`Secure-Loan-Verififaction-and-Approval-system`) and describes the 2023 workflow (Key_generation → Registration → Account_open → Apply_loan → Signin/Login → Display/Remove/Enter_details → Loan_approval → Approval_decision → Loan_details_generation), with no mention of FairLend, LPU, FLA, CKKS gender-only auditing, or any manuscript concept — confirming the User Guide was never updated for the rebrand.
5. **Citation/README block claims this repository is the artifact for "FairLend-Privacy-Preserving-Fair-Loan-Processing" (2025 preprint)**, while every source file's git history places its origin in Dec 2023 under a different project name and problem framing (caste/religion/gender eligibility for a government benefit scheme in an apparent Indian regulatory context, not a LendingClub-based US gender-fairness audit).

## E. Expected non-implementations (correctly out of scope per the manuscript — not bugs)

1. Concrete NIZKP proving/verification (proof sizes, constraint counts, proving/verification time) — manuscript explicitly and repeatedly states this is future work (§4.5.1, §6.4, §7, Table 7 "Not implemented").
2. Repeated ten-seed robustness sweep over α1 ∈ {0.0,0.4,0.7,1.0,1.3} — manuscript explicitly states these numerical results are not included in the present revision.
3. Reproduced proxy-inference AUC — manuscript explicitly declines to claim a specific value.
4. Reproduced encrypted-matching accuracy/macro-F1 numbers — manuscript explicitly declines to report specific values (independent of the separate contradiction at Consistency Finding #1 regarding the reconstruction-error number).
5. Threshold decryption, secure multi-party aggregation, differential privacy, malicious-secure proofs, hardware key custody — all explicitly named in §5 as complementary extensions outside the current prototype.
6. Full malicious-security threat model for Bank/CA/IP/LPU/FLA, and LPU–FLA collusion resistance — explicitly named as outside the stated semi-honest, non-colluding model.

These six items should **not** be treated as repository defects; they are consistent with the manuscript's own stated scope. They are listed here only so they are not mistakenly folded into Sections A–D when this report is acted on.
